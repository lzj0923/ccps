# 收支与维修付款字段未迁移导致500 - 修复报告

## BUG描述

- 页面/功能：管理端“收支与维修”资料载入。
- 操作步骤：管理员进入“收支与维修”页面，前端请求 `GET /api/admin/expenses`。
- 期望结果：正常返回支出与维修列表。
- 实际结果：页面显示“收支与维修资料载入失败”，接口返回 HTTP 500。

## 复现步骤

1. 使用管理员账号调用 `/api/auth/admin/login`，登录返回 HTTP 200。
2. 调用 `/api/admin/expenses?startDate=2026-08-01&endDate=2026-08-26`。
3. 稳定得到 HTTP 500。
4. 在当前 MySQL 执行付款报告字段查询，得到 `ERROR 1054: Unknown column 'pr.fee_account_type'`。

## 根因分析

- 表象：收支与维修接口整体返回 500。
- 根因：代码已经查询新增加的付款报告字段，但当前本地数据库尚未执行 `migrate_payment_report_links.sql`，`payment_receipts` 和 `maintenance_work_orders` 缺少对应列。
- 定位过程：先复现接口 500，再查询 `information_schema.columns`，确认 7 个字段全部缺失；直接执行同一 SELECT 后得到 MySQL 1054，定位为数据库结构与代码版本不一致。

## 修复方案

- 执行 `database/migrate_payment_report_links.sql`，为当前数据库补齐 7 个字段，保留已有记录。
- 新增 `PaymentReportSchemaMigration` 启动迁移：应用启动时通过 JDBC 元数据检查字段，仅补充缺失列；字段已存在时不执行 DDL，避免重复迁移。
- 保留独立 SQL 迁移和部署脚本入口，兼容本地 `spring-boot:run` 与正式部署两种启动方式。

## 单元测试

- 测试文件：`backend/src/test/java/com/ccps/backend/database/PaymentReportSchemaMigrationTest.java`。
- 测试用例：旧数据库缺列时执行 7 条补列语句；字段完整时不执行重复 ALTER。
- 修复前结果：测试编译失败，不存在自动迁移能力。
- 修复后结果：2/2 通过。

## 验证结果

- 当前数据库已确认存在全部 7 个付款报告字段。
- 原接口返回 HTTP 200。
- 返回数据：支出 9 条、维修 2 条。
- 收支与维修账户及导出相关前端测试通过。

## 手动验证步骤

1. 刷新管理端“收支与维修”页面。
2. 确认不再显示“资料载入失败”。
3. 切换“支出”和“维修”页签，确认列表均正常显示。
4. 重新启动后端，再次刷新页面，确认启动迁移不会因重复字段报错。

## 影响范围

- 直接影响：收支与维修列表、付款报告导出。
- 间接影响：新增／编辑支出、维修工单付款资料保存。
- 数据影响：只新增可空字段，没有删除或覆盖现有记录。
