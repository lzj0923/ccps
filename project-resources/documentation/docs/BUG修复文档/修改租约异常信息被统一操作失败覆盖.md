# 修改租约异常信息被统一操作失败覆盖 - 修复报告

## BUG描述
- 页面/功能：租客与租金 / 修改租约。
- 操作步骤：修改租约日期、租客、出租单位或租金条件后保存。
- 期望结果：保存失败时显示后端返回的具体原因，指导用户修改资料。
- 实际结果：页面只显示“操作失败，请稍后再试；如问题持续，请联络管理员”，具体异常被隐藏。

## 复现步骤
1. 让修改租约接口返回 `Lease state changed; reload and try again`（HTTP 409）。
2. 调用前端 `localizeApiErrorMessage`。
3. 修复前结果固定为通用“操作失败”，无法判断是状态冲突、日期问题还是租约不存在。

## 根因分析
- 表象：修改租约弹窗只出现通用错误。
- 根因：`propertyApi.js` 对所有未登记的纯英文服务端异常统一替换为通用文案，丢失了异常内容和 HTTP 状态。
- 定位过程：沿 `submitEditLease → updateAdminLease → request → localizeApiErrorMessage` 追踪，确认表单已正确显示 `error.message`，信息是在请求层本地化时被覆盖。

## 修复方案
- 修改 `frontend/src/services/propertyApi.js`。
- 为修改租约常见异常补充明确中文提示：日期顺序、租约不存在、非有效状态、结束日期已过期、并发修改冲突。
- 对尚未登记的英文异常保留服务端原因，并附带 HTTP 状态，不再统一替换为“操作失败”。

## 单元测试
- 文件：`frontend/tests/admin-tenancy-error-feedback.test.mjs`。
- 用例：`修改租约应显示具体异常原因而不是统一操作失败`。
- 覆盖：已知租约异常中文化、未知异常保留服务端原因及 HTTP 状态。
- 结果：本次相关回归测试 7 项全部通过，前端生产构建通过。

## 手动验证步骤
1. 打开“租客与租金”，选择有效租约并点击“修改租约”。
2. 提交不符合业务条件的日期或已发生状态变化的租约。
3. 确认红色提示显示具体原因，例如“租约资料已被其他操作修改，请重新载入后再试”。
4. 对未登记异常，确认提示包含服务端原因和 HTTP 状态。

## 影响范围
- 直接影响：修改租约失败提示。
- 间接影响：所有使用 `propertyApi.js` 请求封装的管理端操作，在遇到未知英文异常时都能看到具体原因。
- 安全性：后端仍只返回受控异常信息；前端不生成或推测数据库异常内容。
