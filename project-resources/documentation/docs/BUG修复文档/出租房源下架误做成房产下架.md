# 出租房源下架误做成房产下架

## 问题页面 / 功能

- 管理后台：房产管理、租房流程、下架房源
- 功能：下架房源、重新上架招租

## 复现步骤

1. 进入房产管理或租房相关页面。
2. 对一套正在管理的房产执行“下架”。
3. 返回房产管理列表查看该房产。

## 预期结果

下架只代表停止对外招租。房产资产仍应留在房产管理中，业主关系、已有租约、账单、附件、维修与收支记录全部保留；下架资料应在租赁运营的“下架房源”中管理。

## 实际结果

系统把“下架”实现成房产管理状态，导致房产从正常资产清单中隐藏，业务含义错误。

## 根本原因

最初的数据模型把出租房源状态与房产资产状态混为一体，并在房产列表查询中按该状态过滤；入口也错误放在房产管理中。

## 修复方案

- 新增独立的出租房源状态 `rental_listing_status`，只表示是否继续招租。
- 房产管理列表不再按出租房源状态过滤，保证资产始终可查。
- “下架房源”入口移动到租房流程，“下架房源”资料库移动到租赁运营。
- 下架时不结束有效租约，也不中断收租、维修或催缴。
- 重新上架前检查有效出租服务、在管状态及是否存在有效租约，避免重复出租已占用房源。
- 每次下架和重新上架均记录原因、备注、操作人及时间。
- 将本地数据库中误建的房产管理状态字段和历史表无损改名为出租房源状态字段和历史表。

## 测试结果

- 前端专项测试：2 项通过。
- 后端服务测试：4 项通过。
- 前端生产构建通过。
- 数据库迁移后确认 3 套房产均为 `listed`，没有房产因错误状态被隐藏。

## 后续接口异常修复

- 页面首次载入时出现 HTTP 500。
- 根因是普通 MyBatis `@Select` 注解把 SQL 比较符 `>=` 和 `<>` 写成了只适用于 XML 脚本的 `&gt;=` 和 `&lt;&gt;`，MySQL 因而尝试读取不存在的 `gt` 字段。
- 已恢复为原生 SQL 比较符，并增加 `AdminPropertyArchiveMapperSqlTest`，防止普通注解再次混入 XML 转义字符。

## 手工验证要点

1. 房产管理列表应持续显示全部房产资产。
2. 租房流程中可对正在招租的房源执行“下架房源”。
3. 操作后房源从租房流程中移除，并出现在“租赁运营 → 下架房源”。
4. 对存在有效租约的房源执行下架，不应影响租约和日常运营。
5. 有效租约未结束前，系统应阻止重新上架招租。

## 影响范围

涉及出租房源上下架、租房流程筛选、房产列表展示、出租房源历史记录及对应数据库字段；不改变房产资产、租约、账单、押金、附件和维修数据。
