# 下架房源提交 500 - 修复报告

## BUG描述
- 页面/功能：租房流程 / 下架房源
- 操作步骤：选择正在招租的房源，填写下架原因并确认下架。
- 期望结果：房源进入下架房源资料库，已有租约、账单与历史资料继续保留。
- 实际结果：接口返回 HTTP 500，房源未下架。

## 复现步骤
1. 以管理员身份登录。
2. 在租房流程中选择“翻斗花园 · 202”。
3. 选择“业主要求下架”并提交。
4. `POST /api/admin/rental-listings/28/off-market` 稳定返回 HTTP 500。
5. 同一房源的只读上下架记录接口也返回 HTTP 500。

## 根因分析
- 表象：下架提交失败并显示“服务请求失败（HTTP 500）”。
- 根因：MyBatis 查询房源当前状态时，返回类型被定义为 Java 接口 `UnitState`。接口不能被 MyBatis 实例化，因此请求在执行下架写入前已经异常。
- 定位过程：确认数据库中房源、有效租管服务与下架历史数据均正常；再用只读取 `UnitState` 的历史记录接口复现相同 500，最终锁定结果映射类型。

## 修复方案
- 修改文件：`backend/src/main/java/com/ccps/backend/mapper/AdminPropertyArchiveMapper.java`
- 修改内容：将 `UnitState` 改为具有无参构造方法及标准 getter/setter 的可实例化结果对象。
- 修改原因：让 MyBatis 能正确创建对象并映射房源状态字段。
- 同时统一前端业务用语为“下架房源”，移除“停止招租”和“不会下架”的重复、矛盾表达。

## 单元测试
- 测试文件：`backend/src/test/java/com/ccps/backend/mapper/AdminPropertyArchiveMapperSqlTest.java`
- 测试用例：`unitStateQueryUsesInstantiableResultType`
- 测试内容：确保状态查询返回类型不是接口，并具备可调用的无参构造方法。
- 测试结果：通过。

## 手动验证步骤
1. 重启后端以加载修复后的类。
2. 打开“租房流程”，选择一套正在招租的房源。
3. 点击“下架房源”，选择原因并确认下架。
4. 确认不再出现 HTTP 500，房源出现在“租赁运营 → 下架房源”。
5. 打开“上下架记录”，确认下架原因、操作人和时间正确。
6. 确认原有租约、账单和历史资料仍可查看。

## 影响范围
- 直接影响：出租房源下架、重新上架及上下架记录查询。
- 间接影响：无；不修改房产资产、租约、账单及历史资料。
- 回归测试结果：本功能相关 6 个后端测试通过，前端生产构建通过。完整后端测试共 255 个，其中 253 个通过；另有 2 个既有测试因缺少 `owner-tenancy-agreement-template.docx` 模板资源失败，与本次修改无关。
